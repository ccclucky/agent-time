# AgentTime 用户故事

状态：待讨论的产品方案，非已实现功能。本文用于下一版交互原型和 MVP 范围确认，不预设技术栈或采集方式。

## 产品目标

让开发者全面了解自己使用 AI Coding Agent 的时间花销：既能看到指定期间的汇总账本，也能沿着每个数字查看构成、会话、轮次和事件证据。

首页提供明确、易读的核心数据；完整明细应有可发现的入口。数据不完整时仍展示已知事实，但不能把已知部分伪装成完整总数。

“花销”在本阶段以时间为核心。Token 和货币费用是可选扩展；时间、Token 和金额分别汇总，不折算为一个综合分数。

## 汇总账本的提议

首页需要一个有明确名称的“时间花销汇总”，而不只是几个相互独立的指标。

| 汇总项 | 回答的问题 | 计算与展示边界 |
| --- | --- | --- |
| 任务处理累计耗时 | 我交给 Agent 的各轮任务合计花了多久？ | 各已完成 一轮交互 总耗时之和，含人工介入；并行轮次分别累计。只有提交和完成事件时也可能可测量，但不能据此精确拆分工作和人工介入。 |
| Agent 累计工作 | Agent 们合计工作了多久？ | 可测量的工作区间累计，排除人工介入；并行 Agent 分别累计。 |
| 人工介入累计耗时 | 授权、确认、补充信息的请求合计持续多久？ | 完整请求与恢复事件的时长之和；不能解释成用户实际操作或投入的时间。 |
| 用户响应间隔累计 | 完成答复到后续提问的已完成间隔合计多长？ | 区分全部原始间隔和过滤后统计，多个会话的间隔可重叠；不等于用户等待或空闲时间。 |
| 有 Agent 在工作的时长（不重复计时） | 这个期间有多长时间，至少一个 Agent 在工作？ | 工作区间并集，仅覆盖可测量的区间。 |
| 有任务在处理的时长（不重复计时） | 有多长时间，至少一个 一轮交互 处于处理期间？ | 一轮交互 处理区间并集，包含人工介入；不是全天使用跨度或用户真实等待时间。 |

建议在汇总区突出“任务处理累计耗时”，以“Agent 工作 + 人工介入”的构成解释它，并并列提供去重后的覆盖时间。用户响应间隔作为独立一项呈现，不能直接加进任务处理总额。

只有同一组事件完整的轮次，才可显示“任务处理累计 = Agent 工作 + 人工介入”的完整等式。若总耗时已知、拆分未知，增加“构成未知”部分；若时间本身也无法测量，单列未纳入轮次数，不编造时长或完整总额。

会话 总跨度在会话详情中保留。跨会话跨度相加不作为默认“总使用时间”，避免把会话内闲置和会话间重叠误当作实际使用。

示例：A 在 10:00–10:30 处理任务，其中 5 分钟等待授权；B 在 10:15–10:45 连续工作。两轮累计处理 60 分钟，累计工作 55 分钟，人工介入 5 分钟，任务处理覆盖 45 分钟。有 Agent 在工作的时长还取决于授权暂停发生的位置，应以区间并集计算，不能简单用 45 分钟减去 5 分钟。

## 面向用户的语言规范

界面不要求用户先学习我们的数据模型。优先使用熟悉的日常表达；技术名称仅在开发文档或明确标为技术详情的内容中出现。中文页面不直接使用 Turn、Session、Model 作为导航、指标或详情标题。

| 内部术语或原文案 | 建议界面文案 | 首次出现或详情中的解释 |
| --- | --- | --- |
| Session | 会话 | 在同一对话中连续或跨天进行的一组交互；可包含多次提问。 |
| Turn | 一轮交互；列表中写“第 1 轮” | 从你提交一次问题或指令，到 Agent 完成这次答复；中间可能使用工具或请求确认。它不一定等于一个完整任务。 |
| Model | 模型 | Agent 在交互中使用的模型；一个会话或一轮交互可能使用多个模型。 |
| 人工介入耗时 | 等待确认或补充的时间 | Agent 发出确认、授权或补充信息请求，到你完成相应操作的间隔；不是实际操作时间。 |
| 用户响应间隔 | 下次提问前的间隔 | Agent 完成答复后，到你下一次提交的间隔；不是你的实际等待时间。 |
| 去重 / 区间并集 / 工作覆盖 | 有 Agent 在工作的时长 | 多个 Agent 同时工作的一段时间只计一次；提供并排时间线和数值例子解释。 |
| 事件覆盖 | 记录完整性 | 计算这项指标所需的开始、完成、确认和恢复记录是否齐全。 |
| Session 总跨度 | 会话持续时间 | 第一次提问到最后一次已完成答复，包含两次交互之间的间隔；进行中部分另行标识。 |
| P50 / P95 | 一半 / 95% 的交互在多久内完成 | 详情中注明统计口径、样本数及百分位算法，技术简称可作为补充。 |

用词约束：

- 不为了包装产品发明“效率值”“时间信用”等缺少公认含义的词。
- 同一概念在导航、卡片、图表、详情和导出说明中用同一名称；内部字段名可以保留技术术语。
- 总额与累计时长用“时间花销”或“耗时”，货币用“费用”，不混用。
- 不能仅把术语换成中文：文案还要说明起点、终点、是否包含暂停及数据是否完整。
- 单靠悬浮提示不算解释入口；点击、触屏和键盘操作都能打开定义及示例。

## 用户故事与验收条件

### US-01 · 一眼查看指定期间的汇总花销（P0）

作为使用多个 Agent 的开发者，我希望打开 AgentTime 就看到今天、最近 7 天或最近 30 天的汇总账本，以了解自己的 Agent 使用规模和时间构成。

验收条件：

- 汇总包含任务处理累计耗时、Agent 累计工作、人工介入、用户响应间隔以及去重覆盖时长；核心项突出，辅助项可展开。
- 展示会话数、轮次数、时区、时间范围及事件覆盖情况。
- 所有数字遵循当前筛选，不能把不同样本范围的值拼成构成关系。
- 不完整数据明确显示“已知部分”、未知构成和未纳入数量；不将缺失值记为零。
- 已完成统计与进行中活动分开，快照时间可查。
- 无记录显示空状态，而非误导性的全零账单。

### US-02 · 展开汇总花销，核对构成（P0）

作为想核对总额的用户，我希望从汇总入口打开明细账本，以知道花销发生在哪些 Agent、日期、会话 和 一轮交互。

验收条件：

- 路径：总览 → 时间花销汇总详情 → 贡献会话 → 一轮交互 → 事件。
- 详情展示定义、公式、统计范围、构成项、未知项及未纳入数据。
- 支持按 Agent、日期和会话查看贡献；在可可靠归属时提供 模型 维度。
- 分组明细与总额可核对；去重覆盖指标明确不可通过分组时长直接相加还原。
- 从详情返回时保留原筛选与位置。

### US-03 · 解释累计与去重的差异（P0）

作为同时运行多个 Agent 的用户，我希望看到重叠工作区间，以理解为什么累计工作时间可能超过实际经过的时间。

验收条件：

- 路径：总览 → 有 Agent 在工作的时长 → 并行时间线 → 会话。
- 展示累计工作、有 Agent 在工作的时长以及两者差额，并标记重叠区间。
- 两个或更多 Agent 同时工作均按区间并集去重；不能仅逐对相减造成重复扣除。
- 区分工作覆盖和含人工介入的任务处理覆盖，不宣称它们等于用户实际等待时间。
- 差额解释为重复覆盖的累计量；三路并行时不将其误标为一个独立时间段的长度。

### US-04 · 找到花时间最多的会话（P0）

作为希望复盘的开发者，我希望按累计工作、任务处理耗时或 会话 跨度筛选和排序，以找到值得查看的会话。

验收条件：

- 会话列表支持时间范围、Agent 和项目筛选、搜索及指标排序。
- 展示会话标识、Agent、可获取的项目与模型归属、核心耗时及事件覆盖。
- 不可用值不参与数值排名，仍可通过缺失数据筛选找到。
- 点击任意会话进入详情；未知项目或模型保留“未知”，不猜测。

### US-05 · 还原 会话 中每一轮时间（P0）

作为查看长会话的用户，我希望看到每轮执行、人工介入和轮间间隔，以理解 会话 的整体跨度。

验收条件：

- 同时展示 会话 跨度、累计工作、处理耗时和轮次数，解释包含关系。
- 每轮可查看开始、完成、总耗时、工作时间以及人工介入区间。
- 完成答复到下次提交的间隔单独显示；末轮无后续提交时明确标记，不记为 0。
- 同一 会话 跨天恢复仍关联原会话，长间隔被标记。
- 支持多个暂停及未恢复的介入请求；未完成轮次不伪装成已完成数据。
- 事件详情仅需统计元数据，不要求显示 Prompt 或代码。

### US-06 · 清楚知道哪些数据可信（P0）

作为依赖统计作判断的用户，我希望知道每项指标的覆盖和缺失原因，以避免把采集盲区误当成真实使用情况。

验收条件：

- 每项指标可查看完整、部分可测量、不可用或进行中的状态。
- 区分“确认没有人工介入”与“缺少人工介入事件”。
- 总耗时可测量而构成未知时，保留总耗时并显示未知构成。
- 可查看受影响会话及未纳入统计的具体原因。
- 覆盖比例须明确分母是会话、轮次还是其他可观测样本，不能声称代表真实时间覆盖率。
- 区分源数据缺失、适配器不支持、导入失败和真实零值。

### US-07 · 查看长间隔，并控制统计过滤（P1）

作为有时隔天继续会话的用户，我希望查看原始响应间隔，并选择是否过滤长间隔，以得到符合复盘目的的统计。

验收条件：

- 路径：总览 → 用户响应间隔 → 全部间隔 / 长间隔 → 相邻 一轮交互。
- 展示原始累计间隔、过滤后累计间隔、平均值、样本数和被排除数量。
- 阈值可配置，筛选规则在结果旁可见。
- 过滤不修改时间戳、会话 跨度或原始明细；指标明确标注当前口径。
- 未出现下一次提交的间隔不参与已完成间隔统计。

### US-08 · 了解使用习惯和变化（P1）

作为长期使用 Agent 的开发者，我希望按日、周、月查看花销趋势，以了解时间规模和构成如何变化。

验收条件：

- 可在趋势图切换累计工作、任务处理耗时、人工介入和用户响应间隔等指标。
- 点击日期进入对应明细，保留指标和 Agent 筛选。
- 日界线使用明确时区；跨边界的持续时间按与所选期间相交的区间归属，同一规则用于汇总和明细。
- 无采集数据与确认零活动可区分；当前不足周期与完整周期的比较有提示。
- 不把覆盖变化导致的数值变化直接解释为效率变化。

### US-09 · 比较 Agent 和模型的时间分布（P1）

作为使用不同工具和模型的开发者，我希望比较它们的工作量和轮次耗时分布，以发现值得进一步调查的差异。

验收条件：

- Agent、模型 为独立维度，可查看累计工作、样本数、平均每轮、P50 和 P95。
- 展示参与样本、事件覆盖、计算口径及可用的任务背景。
- 会话 切换模型不被固定归到单一模型；多模型 一轮交互 的共享或未知时间不重复计入每个模型。
- 无法归属的时长单列，不强行分摊；模型明细可回到来源轮次。
- 不依据单一耗时给出质量排名或综合效率分数。

### US-10 · 安心接入数据（P0）

作为重视隐私的开发者，我希望在接入前知道会读取什么、保存在哪、哪些指标可用，以放心启用采集。

验收条件：

- 列出支持的 Agent、实际可用的接入方法和必要权限；计划中的适配器明确标识。
- 接入前说明采集字段、存储位置及是否上传，不默认上传 Prompt、代码或敏感内容。
- 完成后展示导入记录、时间范围、事件覆盖和错误信息；不能仅靠按钮状态宣称接入成功。
- 配置页按工具预填默认数据目录，允许自定义、恢复默认和查看目录状态。支持的工具启用后自动发现新会话；未实现的工具只能保存目录，不伪装成接入成功。
- 更换目录和关闭接入保留既有统计；关闭后停止读取该目录中由配置接入的文件。
- 重复导入不会重复计费或累计同一事件。
- 可停止后续采集，并明确停止采集与删除既有数据是不同操作。
- HTML 原型只模拟流程，不能声称已经读取或接入真实日志。

### US-11 · 导出与界面一致的明细（P1）

作为想自行核算的用户，我希望导出当前账本，以在其他工具中复盘或验证计算。

验收条件：

- 导出遵循当前时间范围、筛选、时区和指标口径。
- 包含时间单位、覆盖标记和缺失原因，缺失值不变成零。
- 明确逐行累计字段与不可直接求和的去重指标。
- 默认只导出必要统计元数据；演示数据导出必须标注为演示。

### US-12 · 在来源允许时查看 Token 和金额花销（后续）

作为关心资源成本的用户，我希望在来源提供可靠数据时看到 Token 和金额汇总，以补充时间账本。

验收条件：

- 时间、Token、货币费用分别汇总，各自展示覆盖和来源。
- 区分实际账单金额与基于价格表的估算，并注明模型、价格版本和币种。
- 不将订阅价格或未知费用伪装成逐轮真实成本；不同币种未经明确换算不合并。
- 防止请求重试、缓存和多模型归属造成重复累计；缺失值不记为零。

## 下一版原型的体验路径

1. 总览：看到时间花销汇总、构成、去重覆盖与数据完整性。
2. 点击汇总：展开同一范围内的贡献账本，看到可拆分部分与未知构成。
3. 点击覆盖时长：查看并行时间线，理解累计与实际覆盖的差异。
4. 点击贡献会话：查看 会话 → 一轮交互 → 原始时间事件。
5. 切换闲置过滤：对照过滤前后响应间隔，确认原始数据未改变。
6. 点击覆盖提示：直接找到不能精确拆分的会话及原因。

## 范围与待确认事项

- 建议下一版原型覆盖 P0 路径，并保留现有模型和闲置设置的演示入口；P0/P1 是提议，不代表已接受的开发排期。
- 首批实现已依据[数据源调研](local-adapter-research.zh-CN.md)选择 Codex 只读导入、Python 标准库、SQLite 和本地网页；其他五种适配器及完整事件采集仍待实现。
- 默认核心总额是否采用“任务处理累计耗时”，以及“时间花销汇总”的信息排列，需要通过原型确认。
- 本文不将跨会话响应间隔、会话 跨度、工作时长直接相加成单一“实际等待时间”；若需要个人投入时间，必须另行定义可验证数据源。


### US-13 · 不学术语，也能读懂时间账本（P0）

作为第一次使用 AgentTime 的开发者，我希望只凭页面文字就理解每个数字，以免把一次交互当成一个任务，或把间隔当成自己实际投入的时间。

验收条件：

- 首页、会话列表和详情使用上述面向用户的名称，不要求先理解 Turn、Session 等技术概念。
- 轮次显示“第 1 轮”“共 3 轮交互”，旁边有可发现的说明入口。
- 说明明确“一次提交到一次答复”，并说明工具调用和确认步骤属于该轮；后续提交开始下一轮。
- “累计”与“不重复计时”配有相同数据的数值例子；不能只展示公式或“区间并集”。
- 新用户可沿“这是什么意思 → 怎么算的 → 对应记录”理解指标，不必离开当前统计范围查文档。
- 不把未完成的一轮或多模型调用、子 Agent 活动擅自算作新的用户交互轮次；这些归属规则需要真实数据调研后确认。


## 首批实现与目标故事的差距

当前实现可导入已识别的 Codex 本地记录，查看已记录处理耗时、并行不重复计时、会话与逐轮执行事件。由于历史记录缺少完整审批等待事件和精确用户提交边界，不能声称已经实现完整的工作/等待拆分或用户响应间隔。上述用户故事仍是产品目标，并非首批实现全部验收通过的清单。
